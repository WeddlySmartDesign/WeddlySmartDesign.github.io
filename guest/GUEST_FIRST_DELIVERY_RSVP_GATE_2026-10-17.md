# GUEST — Primera entrega, acceso y RSVP sin editor | 17/10/2026

## Objetivo y límites
Continuar desde `guest/GUEST_MODULE_CLOSEOUT_2026-10-17.md`. La pareja **compra un diseño individual**; WeddlySmartDesign produce, revisa y envía a aprobación; **solo con la invitación final entregada** recibe el acceso a GUEST. Ningún editor de invitación, temas gráficos de la invitación ni configurador de preguntas RSVP forman parte de la app de pareja. Las preguntas las elige en el **cuestionario COMÚN** durante la compra. ONE, Partner, STUDIO y los masters visuales no se modifican. No publicar ventas ni declarar E2E comercial realizado.

## Problema real encontrado y resuelto
El cuestionario ya guardaba `rsvp.menu`, `rsvp.allergies`, `rsvp.plusOne`, `rsvp.children`, `rsvp.customQuestions`, y `practical.bus.enabled` / `practical.accommodation.enabled`, pero al activar GUEST el formulario de confirmación podía seguir creado con configuración **genérica**. Como el editor RSVP fue retirado correctamente para la pareja, la configuración tenía que proceder de un proceso automático, sin pasos manuales.

### Implementación técnica
1. **Servidor `guest-rsvp-ensure` ACTIVE v3**. Código `guest/backend/guest-rsvp-ensure/index.ts`, original exacto `guest/backend/guest-rsvp-ensure/ROLLBACK_LIVE_V2_2026-10-17.ts`. Verifica miembro + licencia + wedding_id. Busca pedido más reciente de `guest_invitation_orders` por `license_id`. Si hay pedido de catálogo y no está **delivered**, devuelve 409 `invitation_not_delivered`. Si está entregado, `catalogueRsvpConfig(order)` construye el formulario con nombres, fecha, lugar/hora, preguntas (menú, alergia, niños, +1, transporte), alojamiento y máximo seis preguntas adicionales tipo texto, con IDs deterministas `catalog_q_1…catalog_q_6`. No inventa preguntas no marcadas. Añade `catalogOrderId` para idempotencia.
2. Si existe formulario activo sin el mapeo para ese pedido, solo lo actualiza **cuando no hay ninguna respuesta registrada**. Con respuestas existentes rechaza con 409 `existing_rsvp_answers_require_review` en lugar de sobrescribir el formulario silenciosamente. Si está ya asociado al mismo pedido, no lo modifica. El caso no-catálogo conserva la configuración anterior para pruebas/legados.
3. `guest/guests-rsvp-operations-live.html` ejecuta `guest-rsvp-ensure` **ANTES** de cargar formularios en la vista de «Envíos y respuestas». No reclama el token genérico antiguo, y no muestra un formulario improvisado cuando falla la inicialización. El backend usa el token de miembro efectivo, también en la modalidad de segunda pantalla.
4. `guest/guests-rsvp-share-composer-v3.js` ya **no reutiliza** el publicToken de localStorage como autorización para otro pedido/boda. Cada intento consulta `guest-rsvp?manage=1` con el token autenticado, solo acepta la `public_token` del formulario activo y borra token local obsoleto si falla. Luego `guests-catalog-invitation-bridge-v1.js` vuelve a validar la invitación definitiva `active_for_member`. Si no hay correspondencia, no genera enlace genérico ni marca envío.
5. **Servidor `guest-license-access` ACTIVE v5**. Código `guest/backend/guest-license-access/index.ts`; copia exacta `ROLLBACK_LIVE_V4_2026-10-17.ts`. La petición `activate` busca pedido vinculado a la licencia. Si el último pedido del catálogo no está **delivered**, rechaza con 409 `invitation_not_delivered` ANTES de emitir un token de miembro o activar boda. Se preservan las operaciones `status`, `invite` y `join` de dos dispositivos y licencias sin pedido de catálogo. Esto convierte el requisito comercial «GUEST solo tras entrega» en **barrera del servidor**, no solo en redacción del correo.

## Flujo automatizado alcanzado
Compra (pagos no habilitados para nuevos diseños) → cuestionario común con opciones RSVP → preparación/revisión/aprobación de invitación → envío final + acceso → **activación solo al constar delivered** → creación/sincronización segura del formulario desde el cuestionario al abrir Envíos → invitados, grupos, unidades y envío por la URL del diseño final → RSVP real desde el mismo GUEST → actualizaciones y segundo dispositivo.
